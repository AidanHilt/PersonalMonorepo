# kubernetes/helm-charts — Implementers

Application and cluster-resource Helm charts, built on the bjw-s common
library chart.

See the [root IMPLEMENTERS.md](../../IMPLEMENTERS.md) for the repo-wide
convention and architecture overview.

## Overview

Two kinds of chart live here:

- An **application chart** (`applications/`) deploys a service that
  affects or expands end-user functionality.
- A **k8s-resources chart** (`k8s-resources/`) creates resources that can
  support multiple apps, or use the configuration from an app.

This directory does not document individual charts — see each chart's own
`Chart.yaml`/`values.yaml` for that. What follows are the conventions
shared across charts.

## Directory layout

- `applications/` — per-application charts (22 currently, e.g.
  `audiobookshelf`, `jellyfin`, `sonarr`), generally based on the bjw-s
  `common` library chart (see "Application chart convention" below).
- `k8s-resources/` — cluster-resource charts, including `master-stack`
  (the chart ArgoCD uses to sync everything else — see
  [kubernetes/argocd](../argocd)).
- `lib/k8s-resources-common/` — a Helm library chart (`type: library`)
  shared between `k8s-resources` charts. See "k8s-resources-common"
  below.
- `templates/` — scaffolds copied by the chart-creation scripts (see
  "Scaffolds and chart creation" below); not charts themselves.

## How it works

### Application chart convention

Every `applications/` chart depends on the [bjw-s `common` library
chart](https://bjw-s-labs.github.io/helm-charts/) (version `1.5.1` in the
current scaffold; see "Gotchas" for `Chart.lock`). The expected pattern,
seen consistently across charts (`applications/jellyfin/templates/common.yaml`
is a good reference; `sonarr`, `radarr`, etc. follow the same shape):

- `templates/common.yaml` calls `bjw-s.common.loader.init`, defines a
  `<app>.hardcodedValues` block of values — env vars, secrets, etc. —
  and merges it into `.Values` with
  `mergeOverwrite .Values (include "<app>.hardcodedValues" . | fromYaml)`,
  then calls `bjw-s.common.loader.generate`.
- App-specific settings live under a `<app>:` key in `values.yaml` (e.g.
  `jellyfin:`, `sonarr:`).
- Credentials/config reach the container via env vars read from a
  Kubernetes `Secret`. That `Secret` is either generated by the chart
  itself (a `secrets.config-secret` block in `hardcodedValues`, gated on
  `<app>.configSecret.existingSecret` being empty) or supplied by the
  caller via `<app>.configSecret.existingSecret`.
- Where an API key is needed, it defaults to `randAlphaNum 32 | lower`
  when `<app>.apiKey` isn't set — see the ArgoCD gotcha below before
  relying on this default.

### k8s-resources-common

`lib/k8s-resources-common` was created in response to a recurring pattern
across `k8s-resources` charts and provides two template functions
(`templates/_enablement.tpl`):

- `common.isItemEnabled` — an item is enabled if `enabled: true` is set
  directly on it, or if it declares a `groupName` and
  `.Values.<groupName>.enabled` is true.
- `common.mergeGroupOverrides` — merges `.Values.<groupName>.<itemName>`
  over the item, falling back to `.Values.<groupName>.default` if no
  item-specific override exists.

Only `master-stack` and `istio-ingress-config` currently declare
`k8s-resources-common` as a dependency — the rest predate it. New
`k8s-resources` charts should adopt it rather than reimplementing the
enablement/override pattern locally.

### Scaffolds and chart creation

`templates/application/` and `templates/k8s-resources/` are plain file
trees with `$CHART_NAME` (and, for k8s-resources, `$RESOURCE_TYPE`)
placeholders, copied and `envsubst`'ed by two scripts:

- [`helm-new-application`](../../nix/scripts/scripts/helm/helm-new-application)
  `--chart-name <name>` → `applications/<name>/`.
- [`helm-new-k8s-resource`](../../nix/scripts/scripts/helm/helm-new-k8s-resource)
  `--chart-name <name> --resource-type <type>` → `k8s-resources/<name>/`.

[`app-creator-create-app`](../../nix/scripts/scripts/app-creator/app-creator-create-app)
is the recommended path for adding a new **application** to a cluster: it
optionally calls `helm-new-application`, then adds the `master-stack`
ArgoCD app entry (`app-creator-add-argocd-app`), ingress, homepage link,
and secrets/Postgres config. Calling the chart-creation scripts directly —
especially `helm-new-k8s-resource`, which `app-creator-create-app` has no
equivalent wiring for — is a valid, supported way to work.

### Validation

`helm lint` is the only validation expected of a chart here. `helm-docs`
is explicitly out of scope as a convention — `paperless-ngx`'s
auto-generated `README.md` is inherited from upstream, not produced by
our own tooling.

### Dormant publishing workflow

`.github/workflows/helm-charts-on-merge.yml` builds and pushes changed
charts to `oci://registry-1.docker.io/aidanhilt`, but is `workflow_dispatch`-only
(manual trigger) and charts aren't actually published anywhere today; it's
slated for deletion.

## Making changes

- New application: see "Adding a new application" in the
  [README](README.md).
- New k8s-resources chart: see "Adding a new k8s-resources chart" in the
  [README](README.md).
- Changing an existing chart's behavior: edit its `templates/`/`values.yaml`
  directly; there is no shared application-chart template beyond the
  `common.yaml` pattern above.

## Gotchas

- **`randAlphaNum` defaults re-render under ArgoCD.** Several charts
  (`jellyfin`, `jellyseerr`, `lidarr`, `prowlarr`, `radarr`, `sonarr`,
  `rxresu`, `tandoor`, `your-spotify`) default an `apiKey`/`secretKey`/
  password-style value to `randAlphaNum 32 | lower` when unset. Under
  ArgoCD, this is expected to behave badly: every refresh re-renders the
  chart, which re-evaluates `randAlphaNum` to a new value each time, so
  the rendered `Secret` never matches the live cluster state — the app
  shows permanently `OutOfSync`, and with `selfHeal` enabled ArgoCD keeps
  re-applying (and re-rotating) the value, which any env-var consumer of
  that key will observe changing. This is reasoned from how `randAlphaNum`
  and ArgoCD's reconcile loop behave, not something observed/confirmed
  against a live cluster. Fix: always set the value explicitly
  (`secureValues`/Vault Secrets Operator — see
  [kubernetes/IMPLEMENTERS.md](../IMPLEMENTERS.md)) rather than relying on
  the random default in any ArgoCD-managed deployment.
- **`jellyfin`'s password secret key is gated on the wrong field.**
  `applications/jellyfin/templates/common.yaml` only writes the `password`
  key into the generated `Secret` when `.Values.jellyfin.username` is set
  (not `.Values.jellyfin.password`) — almost certainly a copy-paste bug
  from the `username` block above it. No other chart's `templates/common.yaml`
  has a `password:` secret key, so this doesn't appear to be shared.
  Documented here, not fixed — fixing chart templates is out of scope for
  this pass.
- **Scaffold `Chart.yaml` ships placeholder versions.** `templates/application/Chart.yaml`
  has `version: 0.0.3` and `appVersion: "2.0.5"` baked in; both must be
  updated per chart after scaffolding (several existing charts still show
  the scaffold's `appVersion` verbatim, suggesting this is sometimes
  missed).
- **`Chart.lock` is inconsistent.** Our workflows generally do not require
  or generate a `Chart.lock`; having one is preferred but not strictly
  required. Some charts have one and some don't — the inconsistency is
  unintentional, not a deliberate per-chart choice.

## Areas for improvement

- **`k8s-resources/prometheus` has no `Chart.yaml`.** It's three raw
  `ServiceMonitor`/`PodMonitor` manifests, not a chart in the same shape
  as everything else here.
- **`k8s-resources/video-stack-configuration` is config-only.** It has no
  workload of its own — see
  [kubernetes/README.md](../README.md#secrets) for why it uses AVP instead
  of VSO.
- **Most `k8s-resources` charts don't use `k8s-resources-common` yet** —
  only `master-stack` and `istio-ingress-config` have adopted it so far
  (see "k8s-resources-common" above).
- **`Chart.lock` inconsistency** across charts (see Gotchas) is unresolved.
