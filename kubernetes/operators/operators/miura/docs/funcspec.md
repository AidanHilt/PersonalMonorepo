# FunctionSpecification

## Purpose

`FunctionSpecification` describes a single Knative function: where its
source lives, how to build it, how it runs, and how traffic (HTTP,
events, schedules) reaches it. It is created either directly by a user,
or generated by a `FunctionRepository` (see [funcrepo.md](funcrepo.md))
from a git repo's directory layout.

## GVK and scope

- Group: `miura.io`
- Version: `v1alpha1`
- Kind: `FunctionSpecification`
- Short name: `funcspec`
- Scope: Namespaced

## Spec fields

Fields marked "op default" have no in-CRD default; the operator-wide
configuration supplies the value when the field is unset.

| Field | Type | Required | Default | Validation | Immutable |
| --- | --- | --- | --- | --- | --- |
| `source.url` | string | yes | — | git `https://` or `ssh://` URL | yes |
| `source.ref` | string | no | `main` | — | no |
| `source.path` | string | no | `.` | relative path, no `..` segments | no |
| `source.secretRef.name` | string | no | — | — | no |
| `source.pollInterval` | duration | no | op default | `0` disables polling; otherwise minimum `30s` | no |
| `build.mainPackage` | string | no | `.` | relative to `source.path`, e.g. `./cmd/hello` | no |
| `build.baseImage` | string | no | op default (distroless static) | — | no |
| `build.env` | map[string]string | no | `{}` | e.g. `CGO_ENABLED`, `GOFLAGS` | no |
| `build.registry` | string | no | op default (in-chart Zot) | — | no |
| `build.imageRepository` | string | no | `<namespace>/<name>` | — | no |
| `build.pushSecretRef.name` | string | no | op default | — | no |
| `runtime.env` | []EnvVar | no | `[]` | standard `corev1.EnvVar` | no |
| `runtime.envFrom` | []EnvFromSource | no | `[]` | standard `corev1.EnvFromSource` | no |
| `runtime.resources` | ResourceRequirements | no | — | standard `corev1.ResourceRequirements` | no |
| `runtime.minScale` | integer | no | `0` | `>= 0`; CEL: `<= runtime.maxScale` | no |
| `runtime.maxScale` | integer | no | op default | `>= 1` | no |
| `runtime.concurrency` | integer | no | Knative default | `>= 1` | no |
| `runtime.timeout` | duration | no | Knative default | — | no |
| `triggers.http` | object | no | — | see below | no |
| `triggers.http.hostname` | string | no | `<name>.<op-domain>` | valid DNS name | no |
| `triggers.http.pathPrefix` | string | no | `/` | must start with `/` | no |
| `triggers.http.gateway.name` | string | no | op default | — | no |
| `triggers.http.gateway.namespace` | string | no | op default | — | no |
| `triggers.http.auth.mode` | enum (`none`, `jwt`) | yes, whenever `triggers.http` is set | — | required with no default when `http` is set | no |
| `triggers.http.auth.jwt.audiences` | []string | required when `mode: jwt` | — | min 1 item | no |
| `triggers.http.auth.jwt.requiredGroups` | []string | no | `[]` | — | no |
| `triggers.http.auth.jwt.requiredScopes` | []string | no | `[]` | — | no |
| `triggers.http.auth.jwt.issuer` | string | no | op default | CEL: both `issuer` and `jwksUri` set, or neither | no |
| `triggers.http.auth.jwt.jwksUri` | string | no | op default | CEL: both `issuer` and `jwksUri` set, or neither | no |
| `triggers.events` | []object | no | `[]` | — | no |
| `triggers.events[].broker` | string | yes (per entry) | — | — | no |
| `triggers.events[].filter` | map[string]string | no | `{}` | CloudEvents attribute filter | no |
| `triggers.schedules` | []object (list-type: atomic) | no | `[]` | — | no |
| `triggers.schedules[].cron` | string | yes (per entry) | — | valid cron pattern | no |
| `triggers.schedules[].data` | object | no | — | CloudEvent payload | no |

CEL validation at the `triggers` level: at least one of `triggers.http`,
`triggers.events`, `triggers.schedules` must be set.

CEL validation at the `triggers.http.auth` level: `jwt` must be set if
and only if `mode == jwt`.

Notes:

- `triggers.schedules[]` entries have no `name` field. The generated
  child `PingSource` name is derived from a hash of `cron` + `data`.
- `auth` lives under `http` (not at the `triggers` level) because
  Knative Eventing deliveries (from `events`/`schedules`) carry no JWT.
  The generated `AuthorizationPolicy` must be scoped to the gateway,
  host, and path used by `triggers.http`, not the whole workload —
  otherwise eventing traffic to the same Knative Service would be
  blocked by a policy meant only for HTTP ingress.
- If `triggers.http` is absent, the generated Knative Service is
  cluster-local (`networking.knative.dev/visibility: cluster-local`)
  and no `VirtualService` is created.
- Build is Go-only, built with `ko` — no Dockerfile is used or
  supported.

## Status and conditions

| Field | Type | Notes |
| --- | --- | --- |
| `status.observedGeneration` | integer | standard observed-generation field |
| `status.conditions` | []metav1.Condition | see condition types below |
| `status.source.resolvedCommit` | string | commit SHA last resolved from `source.ref` |
| `status.source.lastPolledTime` | metav1.Time | last time the operator polled `git ls-remote` |
| `status.image` | string | built image reference, including digest |
| `status.url` | string | externally reachable URL, if `triggers.http` is set |
| `status.builds` | []object | build history, capped at an operator default (e.g. 5) |
| `status.builds[].commit` | string | source commit built |
| `status.builds[].image` | string | resulting image reference |
| `status.builds[].startTime` | metav1.Time | — |
| `status.builds[].completionTime` | metav1.Time | — |
| `status.builds[].result` | string | e.g. `Succeeded`, `Failed` |
| `status.builds[].jobName` | string | name of the backing build `Job` |

Condition types (`metav1.Condition`):

- `SourceResolved`
- `Built`
- `Routed`
- `AuthConfigured`
- `Ready`

Status does not echo any auth configuration (audiences, groups, scopes,
issuer, JWKS URI) — that information lives only in spec.

## Relationships

`FunctionSpecification` owns (via owner references) the following
generated children, created and garbage-collected automatically:

- Build `Job` (runs `ko`)
- Knative `Service`
- Istio `VirtualService` — only when `triggers.http` is set
- `RequestAuthentication` + `AuthorizationPolicy` — only when
  `triggers.http.auth.mode: jwt`
- Knative `Trigger` — one per `triggers.events[]` entry
- Knative `PingSource` — one per `triggers.schedules[]` entry

A `FunctionSpecification` may itself be owned by a `FunctionRepository`
if it was generated rather than user-authored (see
[funcrepo.md](funcrepo.md)).

## Lifecycle and finalizers

No finalizer is used. All generated cluster objects carry an owner
reference back to the `FunctionSpecification` and are garbage-collected
by Kubernetes when it is deleted. Built images already pushed to the
registry are not deleted and remain in the registry.

Immutability: only `source.url` is immutable. All other fields may be
changed after creation and are reconciled in place.

## Open questions

- CORS handling is deferred: preflight `OPTIONS` request bypass of JWT
  auth, and how audience validation should interact with SPA frontends
  making cross-origin calls.
- A possible `forwardAuth` auth mode may be added later; it would
  require a mesh `ExtensionProvider` and is out of scope for v1alpha1.
- Webhook-based rebuild (as an alternative/addition to polling) may be
  added later.
- Per-field immutability is marked conservatively (only `source.url`
  today); other fields (e.g. `build.mainPackage`, `source.path`) may be
  revisited for immutability once reconciliation semantics are better
  understood.
- Exact mechanics of how `ko` is packaged and invoked inside the build
  `Job` (image, flags, credentials wiring) are not yet decided.
