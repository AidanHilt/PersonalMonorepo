# Function

## Purpose

`Function` describes a single Knative function: where its source lives,
how to build it, how it runs, and how traffic (HTTP, events, schedules)
reaches it. It is created either directly by a user, or generated by a
`FunctionRepository` (see [funcrepo.md](funcrepo.md)) from a git repo's
directory layout.

## GVK and scope

- Group: `miura.io`
- Version: `v1alpha1`
- Kind: `Function`
- Short name: `fn`
- Scope: Namespaced

CEL validation at the root level: `metadata.name` must be at most 40
characters.

CEL validation at the `triggers` level: at least one of `triggers.http`,
`triggers.events`, `triggers.schedules` must be set.

CEL validation at the `triggers.http.auth` level: `jwt` must be set if
and only if `mode == Jwt`.

Notes:

- `paused: true` stops polling for new commits and stops starting new
  builds. It does not affect the currently running Knative Service or
  its routes, which keep serving the last successful build unchanged.
  `status.conditions`' `Ready` condition is `False` with reason `Paused`
  while paused.
- `pollInterval` is ignored (no polling occurs) when `source.ref`
  resolves to a tag or a commit SHA, since neither can produce a new
  commit to detect.
- Any change to `source`, `ref`, `path`, or `build.*` triggers an
  immediate rebuild, independent of polling. There is no manual
  trigger mechanism.
- A failed build leaves the previously successful revision serving
  unchanged — `status.image` only ever reflects a successful build.
- The build `Job` is cleaned up automatically via
  `ttlSecondsAfterFinished`; `status.builds[].jobName` may therefore
  reference a `Job` that no longer exists.
- `triggers.schedules[]` entries have no `name` field. The generated
  child `PingSource` name is `<name>-pingsource-<hash8>`, derived from a
  hash of `cron` + `data`. Generated `Trigger` names follow the same
  pattern: `<name>-trigger-<hash8>`.
- `auth` lives under `http` (not at the `triggers` level) because
  Knative Eventing deliveries (from `events`/`schedules`) carry no JWT.
  The generated `AuthorizationPolicy` must be scoped to the gateway,
  host, and path used by `triggers.http`, not the whole workload —
  otherwise eventing traffic to the same Knative Service would be
  blocked by a policy meant only for HTTP ingress.
- If `triggers.http` is absent, the generated Knative Service is
  cluster-local (`networking.knative.dev/visibility: cluster-local`)
  and no `VirtualService` is created.
- Build is Go-only, built with `ko` — no Dockerfile is used or
  supported.
- Images are assumed public: miura ships no in-chart registry (no
  bundled Zot or similar), and `build.registry` defaults to an
  operator-configured external registry when unset.

## Status and conditions

| Field | Type | Notes |
| --- | --- | --- |
| `status.observedGeneration` | integer | standard observed-generation field |
| `status.conditions` | []metav1.Condition | see condition types below |
| `status.source.resolvedCommit` | string | commit SHA last resolved from `source.ref` |
| `status.source.lastPolledTime` | metav1.Time | last time the operator polled `git ls-remote` |
| `status.image` | string | built image reference, including digest |
| `status.url` | string | externally reachable URL, if `triggers.http` is set |
| `status.builds` | []object | build history, capped at an operator default (e.g. 5) |
| `status.builds[].commit` | string | source commit built |
| `status.builds[].image` | string | resulting image reference |
| `status.builds[].startTime` | metav1.Time | — |
| `status.builds[].completionTime` | metav1.Time | — |
| `status.builds[].result` | string | e.g. `Succeeded`, `Failed` |
| `status.builds[].jobName` | string | name of the backing build `Job` (may no longer exist; see notes above) |

Condition types (`metav1.Condition`):

- `SourceResolved` — reasons: `Resolved`, `RefNotFound`, `AuthFailed`
- `Built` — reasons: `Building`, `Succeeded`, `Failed`
- `Routed` — only present when `triggers.http` is set
- `AuthConfigured` — only present when `triggers.http.auth.mode: Jwt`
- `Ready` — reasons include `Paused` (set False while `spec.paused` is
  true); otherwise the logical AND of whichever of the above conditions
  are present for the current spec

Status does not echo any auth configuration (audiences, groups, scopes,
issuer, JWKS URI) — that information lives only in spec.

## Relationships

`Function` owns (via owner references) the following generated
children, created and garbage-collected automatically:

- Build `Job` (runs `ko`)
- Knative `Service`
- Istio `VirtualService` — only when `triggers.http` is set
- `RequestAuthentication` + `AuthorizationPolicy` — only when
  `triggers.http.auth.mode: Jwt`
- Knative `Trigger` — one per `triggers.events[]` entry, named
  `<name>-trigger-<hash8>`
- Knative `PingSource` — one per `triggers.schedules[]` entry, named
  `<name>-pingsource-<hash8>`

A `Function` may itself be owned by a `FunctionRepository` if it was
generated rather than user-authored (see [funcrepo.md](funcrepo.md)).

## Lifecycle and finalizers

No finalizer is used. All generated cluster objects carry an owner
reference back to the `Function` and are garbage-collected by
Kubernetes when it is deleted. Built images already pushed to the
registry are not deleted and remain in the registry.

Immutability: only `source.url` is immutable. All other fields may be
changed after creation and are reconciled in place.

## Open questions

- CORS handling is deferred: preflight `OPTIONS` request bypass of JWT
  auth, and how audience validation should interact with SPA frontends
  making cross-origin calls.
- A possible `forwardAuth` auth mode may be added later; it would
  require a mesh `ExtensionProvider` and is out of scope for v1alpha1.
- Webhook-based rebuild (as an alternative/addition to polling) may be
  added later.
- Per-field immutability is marked conservatively (only `source.url`
  today); other fields (e.g. `build.mainPackage`, `source.path`) may be
  revisited for immutability once reconciliation semantics are better
  understood.
- Exact mechanics of how `ko` is packaged and invoked inside the build
  `Job` (image, flags, credentials wiring) are not yet decided.
- Hostname/gateway allowlisting: nothing today stops a `Function` in one
  namespace from claiming a `triggers.http.hostname` or
  `triggers.http.gateway` that collides with, or hijacks traffic
  intended for, a `Function` in another namespace. Multi-tenant
  allowlisting/conflict-detection for hostnames and gateways is
  deferred to the reconciler implementation.
- Secret key expectations for `source.secretRef` and
  `build.pushSecretRef` (e.g. which keys hold a username/token vs. an
  SSH private key, or registry push credentials) are not yet decided or
  enforced by the CRD schema; the reconciler implementation will need
  to define and document the exact key names it expects.
