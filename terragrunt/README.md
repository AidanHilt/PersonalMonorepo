# terragrunt

Runs the Terraform modules generated by [nix/terraform](../nix/terraform)
(Vault, Vault PKI, Authentik, SeaweedFS), one apply per cluster/module, plus
`staging-cluster/vms` — a plain Terraform (libvirt) module for staging VMs
that doesn't go through `nix/terraform` at all.

See [nix/terraform/README.md](../nix/terraform/README.md) for what the
generated modules actually do (the "helm-linked terraform" concept, module
descriptions, apply order). This README only covers how to navigate and
operate this directory; see [IMPLEMENTERS.md](IMPLEMENTERS.md) for how it
works internally and [IMPROVEMENTS.md](IMPROVEMENTS.md) for known issues.

## Layout

```
terragrunt/
  root.hcl              # shared root config, included by many modules
  <cluster>/             # one directory per environment, e.g. qa-cluster
    env.hcl               # (some clusters) shared inputs merged into every module below it
    <module>/
      terragrunt.hcl        # one Terraform/terranix module (vault, vault-pki, authentik, seaweedfs, ...)
```

A module directory's name must exactly equal the `nix/terraform` module it
builds (`vault`, `vault-pki`, `authentik`, `seaweedfs`), and it must sit
exactly three directories below the repo root
(`terragrunt/<cluster>/<module>/`) — `root.hcl`'s `generate` block resolves
`nix/terraform` with a fixed `../../../` relative path. A cluster
directory's name must match the corresponding
`kubernetes/argocd/configuration-data/<env>/` directory name: that's what
selects which environment's resources get created (see "How an environment
is selected" in [nix/terraform/README.md](../nix/terraform/README.md)).

Some older directories (e.g. `staging-cluster/vms`) use a plain
`terraform { source = ... }` block instead of the `root.hcl`/nix-build flow
described above — they run a plain Terraform module directly rather than a
generated `nix/terraform` package. This is a valid use case

## Prerequisites

- `nix`, with a working `aarch64-linux` builder — every `terragrunt`
  invocation under a module directory using `root.hcl` runs `nix build`
  against `nix/terraform` to regenerate its config (see
  [nix/terraform/README.md](../nix/terraform/README.md)'s "Gotchas" for why
  an `aarch64-linux` builder is required even though the output is
  architecture-independent). If `PERSONAL_MONOREPO_LOCATION` is set in your
  shell and points at an existing local checkout, that `nix build` uses it
  to override the `personalMonorepo` flake input instead of the locked ref
  (see [IMPLEMENTERS.md](IMPLEMENTERS.md)); leave it unset (or point it
  somewhere that doesn't exist) to use the locked ref as before — either
  way the build still succeeds.
- `terragrunt` and `terraform` on `PATH`.
- The environment variables each module's `terragrunt.hcl` reads via
  `get_env(...)` (commonly `VAULT_ADDR`, `VAULT_TOKEN`) actually set in your
  shell — `get_env` with no default fails config parsing if the variable is
  unset.
- For `run_cmd(..., "keepass-retrieve-secret", ...)` inputs: a reachable
  KeePass database and the decryption key configured for
  `keepass-retrieve-secret` (see
  [nix/scripts/scripts/keepass-retrieve-secret/README.md](../nix/scripts/scripts/keepass-retrieve-secret/README.md)).

## State

No remote backend is configured anywhere in this directory — Terraform
state is local to each module directory
(`terragrunt/<cluster>/<module>/.terraform/`, `terraform.tfstate`, etc.,
all gitignored) and is not shared between machines or checked out copies.

## The context workflow

Environment variables and the working directory are normally supplied via
the `nix/scripts` context system rather than set by hand:

1. `context-create-context --name <cluster>` creates a context directory
   (an `.env` plus a `scripts/` dir) — name it the same as the
   `terragrunt/<cluster>` directory you intend to operate on.
2. `context-populate-context --name <cluster> --vault-addr ... --vault-token ...`
   saves variables into that context's `.env`.
3. `context-activate-context --name <cluster>` exports the context's `.env`
   variables into your shell and sets
   `TG_WORKING_DIR=$PERSONAL_MONOREPO_LOCATION/terragrunt/<cluster>` — this
   is why the context name should match the `terragrunt/<cluster>`
   directory name.

See the per-script READMEs:
[context-create-context](../nix/scripts/scripts/context/context-create-context/README.md),
[context-populate-context](../nix/scripts/scripts/context/context-populate-context/README.md),
[context-activate-context](../nix/scripts/scripts/context/context-activate-context/README.md).

## Running terragrunt: `tg`

`tg` (see [its README](../nix/scripts/scripts/tg/README.md)) is a sourced
shell function that wraps `terragrunt`:

- `tg` with no arguments runs `terragrunt` in the current directory.
- `tg <module> <terragrunt args...>` runs
  `terragrunt --working-dir $TG_WORKING_DIR/<module> <args...>` — provided
  `TG_WORKING_DIR` is set and `$TG_WORKING_DIR/<module>` exists; otherwise
  it falls back to running `terragrunt "$@"` directly (so `<module>` would
  need to be a valid `terragrunt` argument itself in that fallback case).

With a context active, `tg <module> plan` / `tg <module> apply` /
`tg <module> destroy` operate on `terragrunt/<cluster>/<module>`.

## Common tasks

### Bootstrap Vault

Vault must be initialized, unsealed, and applied before any other module
(`vault` creates the Kubernetes auth backend every other module reads —
see [nix/terraform/README.md](../nix/terraform/README.md#apply-order)):

1. `vault-initialize` ([README](../nix/scripts/scripts/vault/vault-initialize/README.md))
   against a fresh Vault — saves the unseal keys and root token into the
   active context's `.env`.
2. `vault-unseal` ([README](../nix/scripts/scripts/vault/vault-unseal/README.md))
   to unseal it.
3. `vault-provision` ([README](../nix/scripts/scripts/vault/vault-provision/README.md)),
   or equivalently `tg vault apply`, to apply the `vault` module.

### Apply the other modules

Once `vault` is applied, the rest are order-independent:

```sh
tg vault-pki apply
tg authentik apply
tg seaweedfs apply
```

### Plan / destroy

```sh
tg <module> plan
tg <module> destroy
```

### Add a new module directory

Create `terragrunt/<cluster>/<name>/terragrunt.hcl` where `<name>` matches
an existing `nix/terraform` module name exactly (see "Adding a new module"
in [nix/terraform/README.md](../nix/terraform/README.md) if the module
itself doesn't exist yet). Copy an existing sibling `terragrunt.hcl` under
the same cluster as a starting point (`include "root"`, any module-specific
`inputs`).

### Add a new cluster/environment directory

Create `terragrunt/<name>/`, where `<name>` matches the corresponding
`kubernetes/argocd/configuration-data/<name>/` directory, then add module
subdirectories as above.
