# terragrunt — Implementers

Root Terragrunt config plus per-environment directories that run the
Terraform modules generated by [nix/terraform](../nix/terraform).

See the [root IMPLEMENTERS.md](../IMPLEMENTERS.md) for the repo-wide
convention and architecture overview.

## Overview

This directory is the Terragrunt side of the "helm-linked terraform" setup
described in [nix/terraform/README.md](../nix/terraform/README.md) and
[nix/terraform/IMPLEMENTERS.md](../nix/terraform/IMPLEMENTERS.md): each
module directory here (`<cluster>/<module>/terragrunt.hcl`) drives
`terragrunt` to build and apply one `nix/terraform` package, scoped to one
environment. See [README.md](README.md) for usage and
[IMPROVEMENTS.md](IMPROVEMENTS.md) for known issues; this file only covers
mechanics and gotchas.

## Directory layout

- `root.hcl` — shared Terragrunt root config; generates the Terraform
  config by building the matching `nix/terraform` package for the current
  directory's name (`nix build ../../../nix/terraform/#packages.<system>.<name>`).
- `<cluster>/` — per-environment directories (observed: `qa-cluster`,
  `staging-cluster`, `prod-cluster`), each with per-module subdirectories
  (e.g. `vault/`, `authentik/`) holding a `terragrunt.hcl`.

## How it works

- **Config generation (`root.hcl`)**: every module `terragrunt.hcl` that
  wants the generated flow includes `root.hcl` via
  `include "root" { path = find_in_parent_folders("root.hcl") expose = true }`.
  `root.hcl` declares a `generate "terranix"` block that, at config-parse
  time (i.e. on every `terragrunt` invocation, not just `apply`), runs

  ```sh
  nix build ../../../nix/terraform/#packages.aarch64-linux.<dir-name> && cat result && rm result
  ```

  (`<dir-name> = basename(get_terragrunt_dir())`, i.e. the module
  directory's own name) and writes the JSON output to
  `generated-config.tf.json` in that module directory, overwriting any
  existing copy (`if_exists = "overwrite"`, `disable_signature = true`).
  The `../../../` path is relative to the module directory, so it only
  resolves correctly when that directory sits exactly three levels below
  the repo root (`terragrunt/<cluster>/<module>/`).

  If `PERSONAL_MONOREPO_LOCATION` is set in the shell and points at an
  existing directory, the `nix build` command above instead adds
  `--override-input personalMonorepo path:$PERSONAL_MONOREPO_LOCATION`
  before the flake ref, so the build uses that local checkout of
  `personalMonorepo` instead of its locked/pinned ref. When the env var is
  unset, empty, or doesn't point at an existing directory, the command
  falls back unchanged to the form shown above (non-fatal either way).
  This is the same `PERSONAL_MONOREPO_LOCATION` override pattern used by
  `nix/agentic-ai-stack/flake.nix` (overriding the `scripts` input) and
  `nix/mono-flake/modules/roles/universal/_update.nix`.
- **`result` symlink**: `nix build` creates a `result` symlink in the
  module directory; the `generate` block `cat`s it into the generated
  config and then removes it (`rm result`) in the same command, so it
  shouldn't persist on disk, but a failed/interrupted run can leave it
  behind (it's gitignored either way).
- **Inputs**: module `terragrunt.hcl` files set Terraform variables via
  `inputs = { ... }`. Common patterns:
  - `get_env("VAULT_ADDR")` / `get_env("VAULT_TOKEN")` and similar — reads
    a shell environment variable at parse time; there's no default, so
    parsing fails if the variable isn't set in the shell `terragrunt` runs
    in.
  - `run_cmd("--terragrunt-quiet", "keepass-retrieve-secret", "--secret-path", ..., ["--key-name", ...])`
    — shells out to `keepass-retrieve-secret` to pull a secret value at
    parse time.
  - `basename(dirname(get_terragrunt_dir())) = true` — sets the
    Terraform boolean variable named after the module's *grandparent*
    directory (i.e. the cluster directory) to `true`. This is the
    environment-selection mechanism described in
    [nix/terraform/README.md](../nix/terraform/README.md#how-an-environment-is-selected) —
    the cluster directory name must match a
    `kubernetes/argocd/configuration-data/<env>/` directory name for this
    to enable the right resources.
- **`env.hcl` merging**: some cluster directories have an `env.hcl` with
  its own `inputs = { ... }` block (e.g. shared `vault_url`/`vault_token`/
  `kubeconfig_context`). A module `terragrunt.hcl` that wants those values
  reads it explicitly:

  ```hcl
  locals {
    environment_vars = read_terragrunt_config(find_in_parent_folders("env.hcl"))
  }
  inputs = merge(local.environment_vars.inputs, {
    # module-specific inputs
  })
  ```

  This merge is opt-in per module — a module that doesn't do it ignores
  its cluster's `env.hcl` entirely and must set those inputs itself (see
  [IMPROVEMENTS.md](IMPROVEMENTS.md)).
- **Legacy / non-generated modules**: a few directories skip `root.hcl`
  entirely and use a plain `terraform { source = "<path>" }` block instead
  of `include "root"`, pointing at a plain Terraform module (under
  `terraform/` at the repo root) rather than a `nix/terraform`-generated
  one. These don't get the nix-build generation step, the
  `basename(dirname(...))` environment flag, or any `env.hcl` merge —
  they're a separate, older flow.
- **State**: no `remote_state` block is configured anywhere in this
  directory, so each module directory's Terraform state is local
  (`.terraform/`, `terraform.tfstate*`, all gitignored) — it lives only on
  the machine/checkout that ran `apply`, and isn't shared across machines
  or checkouts.

## Making changes

- **Adding a module to an existing cluster**: see README.md's "Add a new
  module directory" — the directory name must equal an existing
  `nix/terraform` module name, and it must sit at
  `terragrunt/<cluster>/<module>/` (three levels deep) for `root.hcl`'s
  relative path to resolve. Copy an existing sibling `terragrunt.hcl` as a
  starting point.
- **Adding a new cluster**: see README.md's "Add a new cluster/environment
  directory" — the directory name must match a
  `kubernetes/argocd/configuration-data/<env>/` directory name (see
  [nix/terraform/README.md](../nix/terraform/README.md#how-an-environment-is-selected)).
- **Changing what a module reads from Helm values**: that's a
  `nix/terraform` change, not a terragrunt one — see
  [nix/terraform/IMPLEMENTERS.md](../nix/terraform/IMPLEMENTERS.md)'s
  "Making changes", including the `personalMonorepo` push + `nix flake
  update` step.
- **Changing inputs/secrets wiring for a module**: edit its
  `terragrunt.hcl` `inputs` block directly, following the existing
  `get_env`/`run_cmd`/`env.hcl`-merge patterns documented above.

## Gotchas

- **Module directory name must equal a `nix/terraform` module name.**
  `root.hcl` resolves the nix package to build from
  `basename(get_terragrunt_dir())` — a typo or mismatch just fails the
  `nix build`.
- **Module directories must be exactly three levels below the repo root**
  (`terragrunt/<cluster>/<module>/`) — `root.hcl`'s `generate` block hardcodes
  `../../../nix/terraform` as a relative path from the module directory.
- **`aarch64-linux` builder required to even parse a config.** Because the
  `generate` block runs `nix build` at parse time, and `nix/terraform`
  needs a working `aarch64-linux` builder for its import-from-derivation
  Helm-value loading (see
  [nix/terraform/IMPLEMENTERS.md](../nix/terraform/IMPLEMENTERS.md)'s
  Gotchas), *every* `terragrunt` command here — including `plan` — requires
  that builder to be reachable, not just `apply`.
- **Helm values come from a pinned branch, not your working tree —
  unless `PERSONAL_MONOREPO_LOCATION` is set.** Changes to
  `kubernetes/helm-charts/**/values.yaml` or
  `kubernetes/argocd/configuration-data/**` only take effect here once
  they're pushed to the `personalMonorepo` input's pinned branch and `nix
  flake update personalMonorepo` is run in `nix/terraform` — see
  [nix/terraform/IMPLEMENTERS.md](../nix/terraform/IMPLEMENTERS.md) —
  *or* once `PERSONAL_MONOREPO_LOCATION` is exported pointing at a local
  checkout, in which case `root.hcl`'s `nix build` overrides the
  `personalMonorepo` input to that checkout directly (see "How it works"
  above), picking up uncommitted/unpushed local changes without a push or
  `nix flake update`.
- **The config is regenerated on every parse, not cached.** Because
  `if_exists = "overwrite"`, every `terragrunt` invocation re-runs `nix
  build` and overwrites `generated-config.tf.json`, even for read-only
  commands.
- **The `result` symlink is created and removed by the same command.** A
  killed/interrupted run can leave a stray `result` symlink in the module
  directory; it's gitignored, so it's safe to delete by hand if you find
  one.
- **State is local and unshared** — see "How it works" above. There's no
  remote backend, so applying from a different machine/checkout starts
  from empty state.
- **`get_env(...)` values must already be set in the shell `terragrunt`
  runs in**, or config parsing fails outright (no default is passed). The
  context-activation workflow (README.md) is what normally supplies these.
- **Legacy directories bypass all of the above.** Directories using a
  plain `terraform { source = ... }` block instead of `include "root"`
  don't go through `root.hcl` at all — no nix build, no environment flag,
  no `env.hcl` merge.
